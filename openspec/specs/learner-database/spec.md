## Requirements
### Requirement: The application reaches one libSQL database through Drizzle

The application SHALL access its database only through Drizzle ORM over `@libsql/client`, and SHALL build one client per server process from the validated environment (`TURSO_DATABASE_URL`, plus `TURSO_AUTH_TOKEN` when the URL is a remote `libsql://` URL). The client module SHALL be `server-only`. The domain SHALL NOT import it, and adapters SHALL receive the database as a constructor argument, so a test can inject its own.

#### Scenario: The client refuses to reach the browser
- **WHEN** a client component imports the database module
- **THEN** the build fails, because the module is `server-only`

#### Scenario: A remote URL without a token is rejected at startup
- **WHEN** `TURSO_DATABASE_URL` is a `libsql://` URL and `TURSO_AUTH_TOKEN` is unset
- **THEN** the first server access fails with a message naming `TURSO_AUTH_TOKEN`

### Requirement: The server environment is validated in one place

Every server-side environment variable the application reads (database, auth, OAuth, SMTP, Turnstile) SHALL be declared in one Zod schema in a `server-only` module, and SHALL be read only through it. A missing or malformed variable SHALL fail on first use with a message naming the variable. `.env.example` SHALL list every variable, with the values that work against the Compose stack where one exists.

#### Scenario: A malformed variable names itself
- **WHEN** `SMTP_PORT` is `abc`
- **THEN** the first read of the environment fails with an error naming `SMTP_PORT`

### Requirement: Schema changes are versioned migrations

The schema SHALL be declared in TypeScript for Drizzle, and every change SHALL be a SQL migration generated by `drizzle-kit generate`, committed under `drizzle/`, and applied with `pnpm db:migrate`. `drizzle-kit push` SHALL NOT be used against any shared database. Migrations SHALL only add: a destructive change (drop or rename) SHALL be split so the previous release keeps working against the new schema.

#### Scenario: A fresh database reaches the current schema
- **WHEN** `pnpm db:migrate` runs against an empty database
- **THEN** every table in the Drizzle schema exists and `drizzle-kit check` reports no drift

### Requirement: Local development runs the database and the mail inbox in Docker Compose

The repository SHALL ship a `compose.yaml` with exactly two services: `libsql` (image `ghcr.io/tursodatabase/libsql-server` at a pinned version, published on host port `8081`, data in a named volume) and `mailpit` (image `axllent/mailpit` at a pinned version, SMTP on `1025`, inbox on `8025`). Data SHALL survive `docker compose restart`, and `docker compose down -v` SHALL reset it. The Next.js app SHALL keep running on the host with `pnpm dev`.

The repository SHALL provide `db:generate`, `db:migrate`, `db:seed` (a verified learner with a known password), `db:reset` (drop everything, migrate, seed), `db:studio` and `email:dev` (the React Email preview on port `3030`).

#### Scenario: A fresh clone reaches a signed-in app
- **WHEN** a developer runs `docker compose up -d`, `pnpm db:migrate` and `pnpm db:seed`, then `pnpm dev`
- **THEN** they can sign in as the seeded learner

#### Scenario: Port 8080 stays free for the docs
- **WHEN** the Compose stack is up
- **THEN** nothing it starts listens on host port `8080`, which `pnpm docs:serve` uses

### Requirement: Database adapters are tested against a real libSQL server

Every adapter that reads or writes the database SHALL be tested against a real `libsql-server` container started with testcontainers, using the same image version as `compose.yaml`, with the migrations applied before the suite runs. The suites SHALL be skipped, not failed, when Docker is unavailable, as the S3 and GCS blob-store suites already are. They SHALL NOT use mocks, the in-memory adapters or the development database.

#### Scenario: A suite runs against a fresh container
- **WHEN** a database adapter suite runs on a machine with Docker
- **THEN** it starts its own container, migrates it, and leaves no container running afterwards

#### Scenario: No Docker, no failure
- **WHEN** the same suite runs where `docker info` fails
- **THEN** it is reported as skipped and `pnpm test:run` still passes
